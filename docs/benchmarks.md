# Benchmarks

Generated by `benchmarks/run.py`, which builds a synthetic dataset
(10,000 orders, 500 customers, seed 42) and times real queries, median
of three runs.

Run it yourself:

```
PYTHONPATH=. python3 benchmarks/run.py --rows 10000
```

## Numbers from the development sandbox

A 1 GB RAM container, CPython 3.10. Your machine will differ.

| query | squeal | SQLite | slower by |
| --- | --- | --- | --- |
| filter + count | 10 ms | 0.7 ms | 14x |
| group by + having | 19 ms | 2.6 ms | 7x |
| hash join + group | 34 ms | 4.5 ms | 8x |
| window: row_number | 109 ms | 13.6 ms | 8x |
| order by + limit | 29 ms | 0.6 ms | 49x |
| subquery in | 19 ms | 1.1 ms | 18x |
| recursive: 10k chain | 255 ms | 2.1 ms | 121x |

The SQLite column comes from `benchmarks/run.py --compare-sqlite`,
which loads the same generated CSVs into an in-memory SQLite with the
same column types and times the identical query text.

(Numbers wobble run to run on a shared container; treat them as
orders of magnitude, not precise timings.)

## What these numbers taught us

The `subquery in` row used to take **13 seconds**. Three fixes, each
found by measuring:

1. The inner query ran once per outer row. Caching uncorrelated
   subquery results per statement took it to 349 ms.
2. The correlation check re-ran on every outer row. Memoizing the
   verdict took it to 173 ms.
3. The candidate list and probe set were rebuilt per row. Materializing
   both once brought it to about 30-50 ms, the same cost as a plain
   filter over the same rows.

The executor is row-based and interpreted, in Python, with no
prefetching or vectorization. Two more rounds of measurement-driven
work after the subquery fixes:

4. ORDER BY compared rows through a cmp_to_key callback, about 120k
   Python-level calls per 10k-row sort. Stable one-pass-per-key
   decorate-sort with NULL flags took order by + limit from 111 ms
   to 33 ms.
5. WHERE walked the expression tree per row. Compiling the common
   node shapes (columns, literals, comparisons, boolean connectives)
   to closures once per query, with a fallback to the interpreter
   for everything else, took filter + count from 28 ms to 9 ms.
   Schema lookups are memoized along the way.

 SQLite is C with decades of tuning, so the
7x to 121x gap above is the honest cost of that trade. Where the gap
is smallest (window functions, grouping) squeal is doing nearly the
same work SQLite is; where it is largest (recursion, sorting) the
interpreter overhead dominates. It is fast enough to be useful on real
CSVs and slow enough to keep the code honest. That trade is deliberate.

## Columnar experiment

Issue #4 asked what whole-column evaluation buys for the simple scans
that dominate real CSV poking. `squeal/columnar.py` compiles a simple
WHERE clause to one Python list comprehension over column lists and
aggregates with index lists per group. Everything outside the subset
(joins, ORDER BY, DISTINCT, windows, subqueries, HAVING, scalar
expressions in the SELECT list) bails to the row engine.

Run it yourself:

```
PYTHONPATH=. python3 benchmarks/columnar.py --rows 100000
```

Numbers from the same sandbox, 100k orders, median of three:

| query | row engine | columnar | speedup |
| --- | --- | --- | --- |
| filter + count | 111 ms | 40 ms | 2.7x |
| filter + project | 294 ms | 88 ms | 3.4x |
| aggregate | 236 ms | 59 ms | 4.0x |
| group by | 451 ms | 71 ms | 6.4x |
| group by + filter | 172 ms | 84 ms | 2.0x |

The issue asks for a 1M-row CSV; the 1 GB sandbox crawls at that size,
so these ran at 100k. `benchmarks/columnar.py` checks result parity
before timing anything, and `tests/test_columnar.py` holds the two
engines row for row equal across the subset, including NULL three-valued
logic, mixed-type comparisons, and NULL group keys.

Independent review of this experiment (separate harness, not the repo's
test collection): roughly 23,000 random subset and non-subset queries
across six seeds compared type-sensitively against the row engine, plus
42 handcrafted edge queries - zero mismatches. The reviewer also ran
hostile literals and column names carrying injection payloads; their
canary check created no marker files, meaning no injected code ever
executed. A one-run repetition
of the table above on the same 100k rows measured 2.1x, 3.6x, 3.7x,
4.7x, and 1.2x - same direction, noisier. Nobody has measured 1M rows,
memory use, or concurrency; treat all of this as evidence, not proof.

What the experiment does not do: beats SQLite. The columnar filter +
count above runs 40 ms on 100k rows (0.4 us per row); SQLite runs a
similar query shape in 0.7 ms on 10k rows in the table at the top
(0.07 us per row). That is roughly 6x per row on similar query shapes
and different datasets, even after the columnar win:
real, but a constant-factor win inside a pure-Python interpreter, not
a new league.
